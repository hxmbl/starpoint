# Next tasks

This file tracks work that remains after the current implementation. Completed items are recorded in the completion summary so this list stays actionable.

## Remaining core work

1. **Recover interrupted package-manager operations.** Starpoint currently detects and safely cleans stale config-writer temporary files. Provider operations are still recovered by re-inspecting inventories and PATH when the command is rerun; Starpoint does not yet persist a journal for every provider subprocess. Add explicit operation records only where provider state alone cannot safely identify progress.
2. **Expand executable-to-package mappings.** The locator supports provider mappings and uses them for ownership attribution, but only a subset of providers maps executable names back to package names. Add mappings as provider inventory semantics are confirmed, especially for multi-binary packages.
3. **Improve project-context coverage.** Project detection reads Rust and Go toolchain declarations and contributes project ecosystem context to provider resolution. `install .` runs the ecosystem's own dependency installer (npm/pnpm/yarn, uv/pip, cargo, go, bundler) chosen from lockfiles; it never mutates project manifests. Add ecosystems with clear ownership and lockfile behavior (Poetry, Pipenv, Bun, Composer), and consider honouring declared toolchain versions.

## Remaining CLI and API work

4. **Publish the JSON schema as a machine-readable artifact.** `docs/json-schema.md` documents the current schema version and the command shapes. Generate or validate a formal JSON Schema document from the actual Go output types so external clients can validate payloads without duplicating the prose contract.
5. **Generate shell completions.** Bash, zsh, and fish completions are hand-written; a test (internal/cli/completions_test.go) checks them against the command, flag and provider tables. Generating them from those tables would remove the duplication. The zsh and fish files have not been exercised in a real shell in CI.
6. **Improve PATH inventory controls.** `doctor` summarises the PATH inventory (counts, shadowed names, unknown owners; `--all` for everything) and PATH directories are de-duplicated by real path. `list` still prints every unaccounted executable; consider the same summary there and richer filters (by directory or owner) for very large PATHs, keeping the full data in machine output.

## Open product decisions

- **Planned `cargo install` paths for crates Starpoint does not know.** A planned install names the command from Cargo's inventory (installed crates) or a short table of known renames (ripgrep → rg, fd-find → fd, ...); any other crate is assumed to install a command named after itself, and the planned effect says so. crates.io's API lists each version's `bin_names`, which would make this exact at the cost of a network request during planning (and a dry run). Recommendation: do it only behind the same timeout and offline fallback as `cargo search`, if planned paths for unknown crates turn out to matter.
- **Per-command privilege for location-dependent providers.** npm, pnpm, yarn and gem are classified once per run by where they install: a system prefix runs every one of their commands as root, inventory included. Running read-only commands as the user and only mutations as root would be possible, but would let a provider's inventory and its installs disagree about whose files they are. Recommendation: keep one account per provider per run unless a concrete case needs otherwise.
- **Show the privilege classification in `doctor`.** Under sudo, `doctor` reports the elevation and any failure to drop privileges, but not which account each provider would run as; that is visible per action in `run_as` and `--verbose`. Classifying npm, pnpm, yarn, gem and brew means asking each for its prefix, so `doctor` would gain five subprocesses under sudo. Recommendation: add it if users ask "what will sudo do?" before running it.
- **Should `--allow-destructive` have a narrower form?** It allows every destructive effect of the run. A per-kind allowance (`--allow-destructive=config`, `=replace`) would let an agent accept, say, a pin rewrite without accepting a deletion. Recommendation: wait for a concrete caller that needs it.

## Provider coverage

7. **Add more providers when ownership is reliable.** Bun, Deno, Nix, mise, asdf, Flatpak, Snap, winget, Chocolatey, and additional language providers remain candidates. Each provider should support useful inventory and ownership reporting before it is used for automatic resolution.
8. **Provider-specific version constraints.** Exact pins are supported where providers can honor them. Ranges and richer constraint syntax remain deferred until a concrete provider requires them; parsing must stay provider-specific.
9. **Inventory pass consolidation.** Planning and ownership reporting may query provider inventories more than once. Revisit if profiling shows this is a material latency problem.
10. **Newest-version lookups for more providers.** Pin conflicts are detected for pip, npm, pnpm, Homebrew, Cargo, RubyGems and APT. uv has no index query of its own; yarn, Go, DNF and Pacman are also unimplemented.

## Settled behavior

- Project configuration is additive to global configuration. A project entry with the same package name overrides the global entry; other global packages remain desired.
- `scope = "project"` is accepted as placement intent, but providers that cannot install into a project context report that limitation. Starpoint does not silently rewrite a project's manifest to manufacture support.
- `install .` records the toolchain a project needs (node, cargo, go, ...) in the project's own `.starpoint.toml`, creating it if necessary, and never installs a toolchain implicitly. Project dependencies are installed by the ecosystem's own tool after confirmation.
- `update` never moves a pin silently. A newer version than the pin is reported as a conflict and asked about; yes updates and rewrites the pin to the installed version, anything else (including `--no-confirm`) keeps it. `sync` still converges on the pin without asking.
- `sync` does not adopt an installation merely because it exists. `starpoint install` is the explicit adoption path and records the selected provider in the source of truth.
- An explicit provider in configuration wins. Otherwise an existing non-system owner is retained, known executable ownership mappings are considered, then ecosystem and project context guide a choice. Starpoint asks when multiple viable general providers remain ambiguous.
- Transition phases are reconstructed from provider inventory and executable resolution. Re-running a transition resumes based on observed machine state; the history store supports audit and explicit reversal.
- An unattended run (`--yes`/`--no-confirm`, `no_confirm = true`, or stdin that is not a terminal, a piped answer included) that would delete or replace anything is refused without `--allow-destructive`, with exit 3 and the full planned effect list. Interactive runs keep the confirmation step, which lists destructive effects; dry runs are never refused.
- A changing command run as root or elevated is refused without `--allow-root` (exit 4). Under sudo or doas at a terminal an explicit yes stands in for it; `--yes` does not. Read-only commands and `doctor` always run. Under sudo or doas from an ordinary user the run acts on that user's environment and gives them what it writes there; a plain root run acts on root's environment. What an elevated run creates in shared locations is made world-readable and executable.
- Effects are watched in a bounded set of directories, grown per provider (uv, pip, Cargo and Go executable directories so far). The home directory is never snapshotted.
- Under sudo or doas from an ordinary user, each provider runs as the account its work needs, decided once per run: uv, pip (always `--user`), Cargo, Go and rustup as the invoking user; npm, pnpm, yarn and gem as the user when their prefix is in the user's home or owned by them, otherwise as root; Homebrew as the user when its prefix is theirs; apt, dnf, pacman and the system provider as root. A user who cannot be resolved, or a failed attempt to start a process as them, refuses changing commands (exit 4) rather than running their providers as root. Starpoint's own files are written by Starpoint and given back to the user at the end of each command.
- Removing every configured package in one command is refused without `--allow-empty`. Removing one package is ordinary and never refused.
- Prune removes only orphaned user-scoped software that a provider can enumerate and remove. It excludes system/global scope and configured package names. It refuses when the configuration declares no packages, because there is then no source of truth to tell managed software from orphans, and it lists its candidates in both the human and JSON forms of `--dry-run`.

## Completed in this implementation

- Crash recovery detection and safe cleanup for stale Starpoint TOML temporary files, with ambiguous or sole-copy data preserved. Config writes are flushed and renamed atomically, so an interrupted run cannot leave a half-written config; `starpoint recover` reports leftover files and `--discard` clears them.
- Per-config mutation locks around state-changing CLI operations.
- `starpoint prune`, with preview, confirmation, scope protections, and JSON output. It refuses when the configuration declares no packages, and its `--dry-run` lists the candidates in both human and JSON output.
- Transition history and `starpoint transition --reverse`.
- PATH executable inventory with symlink/duplicate reporting in `list` and `doctor`.
- Resolver explanation through `starpoint explain <package>`.
- Versioned JSON output envelope and command-shape documentation. Every command emits one flat object under schema version 2, so the documented shape and the emitted shape cannot drift.
- `info --json` emits a single document: the provider survey or a pending transition travels inside the same response instead of in a second JSON object.
- `prune` refuses to run when the configuration declares no packages, and `--dry-run` lists the candidates in both human and JSON output.
- Removed the vestigial `--record` flag, which was accepted but did nothing (recording is automatic), and the unused `internal/starpointcontext` package, which duplicated `internal/project`.
- An append-only audit log of every command and every change to the machine, in `~/.starpoint/logs/`, rotated daily. Failures and refusals are recorded, not just successes.
- Retention across every store — audit log, transition history, run history — applied automatically on every command, configurable with `retention_days` (default 30). `history.Prune` existed but nothing ever called it.
- `starpoint logging [prune|config]`, reporting and configuring retention, plus generation of the system's own rotation configuration: logrotate on Linux, newsyslog on macOS, nothing on Windows. Starpoint writes only inside its own state directory and prints the privileged install step instead of taking it.
- A guard on `remove`: removing every configured package in one command requires `--allow-empty`. A single removal is unaffected, and a dry run is still allowed to describe the change.
- All of Starpoint's records now live in a state directory derived from the global configuration path, so a run against another configuration — including the test suite — writes nothing into a real home directory.
- Bash, zsh, and fish completion scripts.
- TOML writes that preserve comments and unrelated file content while updating package entries.
- DNF and Pacman providers alongside the existing APT and Homebrew integrations. Neither can honour an arbitrary version pin, and both report that rather than claiming a capability they lack.
- Optional provider executable verification after install/update and during transitions.
- Rust `rust-toolchain` / `rust-toolchain.toml` and Go `go.mod` toolchain declaration detection.
- Per-action transparency (JSON schema 5): every action reports its outcome, provider and version transitions, configuration changes, and effects observed on disk (paths created, modified, replaced or deleted, packages, PATH resolution, shell profiles) with a destructive flag, plus coded warnings attached to their package and a top-level summary. Confirmation steps and results list destructive effects; `--dry-run` and `--verbose` list them all. The audit log records each applied action's effects, and whether a command ran elevated.
- A `running-elevated` warning on every changing command and in `doctor` when Starpoint runs as root or elevated.
- `--allow-destructive`: an unattended run (`--yes`/`--no-confirm`, `no_confirm`, or stdin that is not a terminal) that would delete or replace anything is refused with exit 3, the coded error `destructive-unattended`, and the full planned effect list in human and JSON output (JSON schema 6). Interactive runs keep the confirmation step.
- `--allow-root`: changing commands are refused as root or elevated (exit 4, `elevated-refused`) unless the flag is given or, under sudo or doas at a terminal, the user confirms. Under sudo or doas Starpoint acts on the invoking user's environment (HOME, configuration, ~/.local/bin) and aligns what it touches: what it writes under that home, the providers' state directories there, and Starpoint's own records are given to that user; what it creates in shared locations is made world-readable and executable. Each fix is a `chown` or `chmod` effect in the action's output and the audit log, and a failed fix raises `permission-fix-failed`.
- Running user-level providers as the invoking user (JSON schema 7). Under sudo or doas from an ordinary user, user-level providers run with the user's uid, gid and supplementary groups (`SysProcAttr.Credential`, Linux and macOS) and an environment built for them (`internal/privdrop`): HOME, USER, LOGNAME, their shell, a PATH led by their tool directories, their own XDG_RUNTIME_DIR, and only location variables that point into their home; nothing pointing into root's home is passed on. System providers keep running as root. A probe (`id -u` as the user, and a writable home) runs before anything changes; an unresolvable user or a failed probe refuses changing commands with `invoking-user-unresolved` or `privilege-drop-failed`. Each action reports `run_as` (user, uid, gid, elevated, dropped, privilege, reason) in JSON, the audit log and `--verbose`. `internal/align` stays as the safety net: a root-owned entry found in the user's home after a dropped run is still given back, marked `unexpected`, with a `root-owned-after-drop` warning; what the user wrote keeps the user's modes. The project installer of `install .` runs as the user when the project directory is theirs. Windows has nothing to drop and is unchanged.
- pip and npm state under an elevated run: pip runs as the user, and its user site-packages is checked as a state directory; npm's cache and global modules are state directories under the user's home, and an elevated npm into a system prefix has its package directory (`<prefix>/lib/node_modules/<name>`) widened like the executable it links.
- Planned `cargo install` paths name the command a crate installs when Cargo's inventory or a table of known renames knows it (ripgrep → `~/.cargo/bin/rg`), and say when the crate's own name is only assumed. A multi-binary crate's recorded path is its first command rather than its last.
- Cargo and Go report their executable directories (`CARGO_INSTALL_ROOT`/`CARGO_HOME`/`~/.cargo` bin; `GOBIN`/`GOPATH` bin/`~/go/bin`), so what they write there is observed. The watched set stays bounded (never the home directory or an ancestor), and a file already at the target's path counts as a shared executable only when it belongs to the provider being moved away from.
